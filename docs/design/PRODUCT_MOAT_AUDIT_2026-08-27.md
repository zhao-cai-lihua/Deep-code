# Deep code 产品壁垒审查（2026-08-27）

## 结论

Deep code 的壁垒不应是“也有聊天、侧栏、主题、生态列表”。这些都是必要的产品卫生，但成熟客户端很容易复制。真正值得持续投入的是一条可验证的翻译链：**Harness 事实 → 面向普通人的当前状态 → 能理解的结果 → 能执行的恢复动作**，同时始终保留证据入口。

## 已形成差异的能力

1. **来源感知的 Conversation / Trace 投影**：不把系统注入、工具事件、人的原话和最终答复混成 CLI 流。
2. **不越权的 Decision Gate**：将官方 approval/question 翻译成人的选择；表单可留置，超时不代答，并把等待原因写入恢复状态。
3. **证据约束的 Outcome / Recovery**：只从 Engine 终态、文件 presenter、测试/构建结果和失败工具生成结论，不用模型自夸证明完成。
4. **附件提交原子性**：图片只有在官方 prompt 接受后才离开发送区；失败仍可恢复。
5. **受控生态安装**：把“热门仓库”与“可信插件”分开；固定源码、检查 Bundle、提示安装期代码风险，再调用官方 profile，不执行网页给出的命令文本。

这五项共同构成 Soft Harness：不是更换 Agent 的脑子，而是降低人理解状态、作出决定和从失败恢复的成本。

## 必须有，但不构成壁垒

- 左侧任务与工作区导航；
- 深浅主题、玻璃质感、动效与图标；
- Markdown、复制、滚动跟随；
- GitHub 高星项目聚合；
- Engine 路径与诊断日志。

这些功能要做稳、做美，但不应占用核心架构的复杂度预算。优先复用原生 Harness/Codex 已验证的交互规律。

## 当前仍然薄弱

1. 插件安装已经真实落盘，但尚缺“已安装列表、卸载、重启后生效验证、失败前后 profile 快照与回滚”。因此测试版必须明确标为 Beta。
2. Outcome 能说明已确认事实，尚未覆盖依赖变更、跨文件影响和测试遗漏的结构化关联。
3. Recovery 对等待超时已有专门路径，其余错误仍需要按认证、网络、模型能力、权限、工作区和上游协议变化分类。
4. 上游协议兼容目前靠自动测试保护已知形状，尚缺针对多个 DSH 版本的契约矩阵。

## 暂不恢复的设计

角色卡/回复模式不进入当前 MVP。此前的实现既没有可见效果证据，又可能反复占用上下文，并会模糊“偏好表达”和“执行权限”的边界。旧的本地草稿文件不主动删除，但产品不加载、不注入、不展示它们。未来若重启该方向，必须以可测量的回复差异、每轮 token 成本、明确启用范围和零权限提升为准入条件。
